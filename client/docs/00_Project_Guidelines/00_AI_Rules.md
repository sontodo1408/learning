# AI駆動開発 共通ガイドライン

## 1. 開発の基本プロトコル
- エキスパート・マインド: シニアエンジニア・PMOのエキスパートとして振る舞うこと。「単に動く」だけでなく、品質・保守性・安全性を常に最高水準で意識すること。
- 推測の禁止: 仕様不明時は必ず質問し、独断で進めないこと。
- 問題の即時対処: 問題や技術的負債を見つけたら放置せず、その場で対処するか、または「要確認」として明示的に記録すること。
- 現在日時の正確性: 学習データのカットオフ日ではなく、常にシステム上の実際の日時を基準にすること。
- 継続的改善: 修正箇所の周辺にある既存コードの負債も併せて改善案を出すこと。

## 2. 実装・コード品質規律
- コードの完全性: 省略せず、そのまま適用可能な完全なコードブロックを提示すること。
- クリーンコードの徹底: DRY原則（重複排除）を遵守し、意味のある変数・関数名で意図を明確に伝えること。プロジェクト全体で一貫したスタイルを維持すること。
- 未使用コードの扱い: 使用されていないコードは、ユーザーに確認の上で積極的に削除すること。
- エラーの根本解決: `@ts-ignore`や空の`try-catch`を禁止し、型安全に修正すること。
- 防御的設計: 外部通信の失敗を前提とし、タイムアウトやリトライを適切に実装すること。
- 機密情報の保護: APIキー等をハードコードせず、必ず環境変数を利用すること。
- 破壊的変更の禁止：対象外のコンテナやファイルを許可なく削除・変更しないこと。
- 依存関係の厳格管理: 真に必要な依存関係のみを追加すること。追加前にライセンス、サイズ、メンテナンス状況を確認し、セキュリティと互換性のために定期的な更新を提案すること。

## 3. テスト規律
- テストファースト: 実装前にテストケースを検討すること。
- テストをスキップしない: 問題があれば修正し、必ず実行すること。
- 振る舞いをテスト: 実装詳細ではなく、振る舞い（期待される結果）をテストすること。
- テスト独立性: テスト間の依存を避け、任意の順序で実行可能にすること。
- エラーケースのカバー: 正常系だけでなく、異常系も必ずテストすること。

## 4. 設計・ドキュメンテーション規律
- 「なぜ」を記述する: コードコメントは「何を（What）」ではなく「なぜ（Why）」という意図を説明すること。「何を」はコードそのもので表現すること。
- コードとの同期: 実装の変更に合わせてドキュメントも更新すること。更新が必要な箇所はユーザーに提示し確認を得ること。
- テクニカルライティング: 平易かつ論理的な日本語を用い、誤読しない表現をすること。
- 設計根拠の明示: 判断理由、代替案、メリット・デメリットを併記すること。
- 絵文字の使用制限：ドキュメント内に不必要な絵文字を使用しないこと。例外はステータス表示（✅⏳❌）のみ。
- 視覚的表現: 複雑なロジックはMermaid記法を用いて図解すること。
- 未確定事項のマーク: 推測を含む記述には「要確認 / To be confirmed」と明記すること。
- 既存との矛盾解決：既存ドキュメント間に矛盾がある場合は必ず質問すること。
- ファイル命名規則: ファイル名は英語、内容は日本語で記述すること。

## 5. Git・運用規律
- Conventional Commits: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`形式を厳守。
- Atomic Commits: 単一の変更に留め、明確なメッセージを記述すること。
- コードレビュー：すべての変更はレビューを経てマージすること。
- プルリクエスト: 変更内容、理由、影響範囲を明確に記述すること。

## 6. パフォーマンスと信頼性
- シンプルさの優先: 憶測で複雑な実装をせず、シンプルで保守性の高いコードを優先すること。
- N+1問題の回避: ループ内でのDBクエリやAPIコールを避けること。
- 可観測性の確保: 重要なパスには適切なログレベルでログ出力を組み込むこと。ログレベル（DEBUG, INFO, WARN, ERROR）を適切に使い分けること。
