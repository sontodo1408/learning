## 概要

### **このワークフローの目的**

1. **設計の一貫性確保**: DB → 画面 → API → 詳細設計の順序で整合性を保つ
2. **手戻りの最小化**: 各フェーズで整合性を確認し、後工程での手戻りを防ぐ
3. **AI駆動開発の効率化**: 明確な順序と成果物で、AIが効率的に設計を支援
4. **品質の担保**: 各フェーズでレビューポイントを設け、品質を確保

### **現状の整備状況**

**プロジェクト開始前の準備**:
- プロジェクトガイドライン整備
- 各設計書のガイドライン・テンプレート作成
- 顧客承認済みモックアップ（必要に応じて）
- データベース設計の準備（ER辞書、テーブル一覧テンプレート）

⏳ **これから詰める部分**:
- 詳細設計書の作成

## 設計フローの全体像

### **設計の順序**

```
要件確認 → DB設計 → 画面設計 → API設計 → 詳細設計 → 整合性確認 → レビュー → 実装
```

### **各フェーズの関係**

- **DB設計**: データ構造の基盤（Single Source of Truth）
- **画面設計**: ユーザー体験の定義（モックアップベース）
- **API設計**: フロントエンドとバックエンドの契約
- **詳細設計**: ビジネスロジックの実装方針

### **重要な原則**

1. **上流から下流へ**: DB → 画面 → API → 詳細設計の順序を守る
2. **整合性の継続的確認**: 各フェーズで前工程との整合性を確認
3. **ドキュメントファースト**: 実装前に設計書を完成させる
4. **モックアップを真実とする**: 画面設計はモックアップに準拠

## イテレーション戦略

### **機能単位でのイテレーション**

設計は機能単位で進め、すべての機能を一度に設計しない。

### **イテレーション設計の例**

プロジェクトの規模や複雑度に応じて、機能をイテレーションに分割して設計を進めることを推奨します。

#### **イテレーション分割の考え方**
- 依存関係の少ない機能から着手
- マスタデータ → トランザクションデータの順
- コア機能 → 付加機能の順

#### **例: タスク管理システムの場合**

**Iteration 1: 基本マスタ・認証**
- **DB**: `users`, `roles`, `user_roles`
- **画面**: ログイン、ユーザー管理
- **API**: 認証API、ユーザーCRUD API
- **詳細設計**: 認証ロジック、ユーザー管理ロジック

**Iteration 2: プロジェクト管理**
- **DB**: `projects`, `project_members`
- **画面**: プロジェクト一覧、プロジェクト詳細
- **API**: プロジェクトCRUD API
- **詳細設計**: プロジェクト管理ロジック

**Iteration 3: タスク管理**
- **DB**: `tasks`, `task_assignments`
- **画面**: タスク一覧、タスク詳細
- **API**: タスクCRUD API
- **詳細設計**: タスク管理ロジック、ステータス遷移ロジック

**Iteration 4: コメント・添付ファイル**
- **DB**: `comments`, `attachments`
- **画面**: コメント表示、ファイルアップロード
- **API**: コメントAPI、添付ファイルAPI
- **詳細設計**: コメント投稿ロジック、ファイルアップロードロジック

**Iteration 5: ダッシュボード・レポート**
- **DB**: 既存テーブルからの集計
- **画面**: ダッシュボード
- **API**: 集計API
- **詳細設計**: 集計ロジック

**Iteration 6: 統合・最終化**

##### 成果物
- 全体ER図
- 制約・インデックス設計
- DDL生成

##### 整合性確認チェックリスト

**1. テーブル定義の完全性確認**
- [ ] テーブル設計書の全テーブルがDDLに存在する
- [ ] 各テーブルの全カラムがDDLに存在する
- [ ] カラムの型がテーブル設計書と一致する
- [ ] NOT NULL制約がテーブル設計書と一致する
- [ ] デフォルト値がテーブル設計書と一致する
- [ ] UNIQUE制約がテーブル設計書と一致する

**2. 制約の完全性確認**
- [ ] 主キー（PK）がすべて定義されている
- [ ] 外部キー（FK）がすべて定義されている
- [ ] CHECK制約が適切に定義されている
- [ ] CHECK制約のカラム名が正しい（typoがない）

**3. ドキュメント間の整合性確認**
- [ ] 個別テーブル設計ファイル ⇔ テーブル一覧
- [ ] テーブル一覧 ⇔ DDL（CREATE TABLE文）
- [ ] テーブル設計書 ⇔ ER図

**4. 命名規則の確認**
- [ ] テーブル名がスネークケース（snake_case）
- [ ] カラム名がスネークケース（snake_case）
- [ ] 外部キー名が規則に従っている（fk_テーブル名_参照先）

**5. コメントの確認**
- [ ] すべてのテーブルにCOMMENTが定義されている
- [ ] 重要なカラムにCOMMENTが定義されている

**6. 整合性確認レポートの作成**
- [ ] 発見された問題点を記録
- [ ] 実施した修正内容を記録
- [ ] 再発防止策を記録


## 機能追加・変更時の衝突検出ルール

### **必須プロセス**

機能の追加または変更を行う際は、以下のプロセスを**必ず**実行すること：

#### **1. 事前分析フェーズ**

新規機能追加または既存機能変更の要求を受けた場合：

**関連ドキュメントの全件検索**
- `docs/01_Business_Process/` 配下のすべての要件定義書を確認
- `docs/03_Database_Design/` 配下のすべてのDB設計書を確認
- `docs/04_Screen_Design/` 配下のすべての画面設計書を確認
- `docs/05_API_Design/` 配下のすべてのAPI設計書を確認
- 特に以下の項目を重点的にチェック：
  - 同様の機能が既に存在しないか
  - データモデルの重複や矛盾がないか
  - インターフェース定義の競合がないか
  - 非機能要件への影響がないか

**衝突・矛盾の検出**

以下のいずれかに該当する場合は**即座に作業を停止**：
- 既存機能と責務が重複する
- データベーススキーマに矛盾が生じる
- API仕様に不整合が発生する
- 非機能要件（性能、セキュリティなど）に抵触する
- 要件の曖昧さや不明確な点がある
- 複数の解釈が可能な仕様である

#### **2. 確認フェーズ**

衝突・矛盾・不明確な点を検出した場合：

**作業の即時停止**
- ドキュメントの変更を行わない
- 一切の編集作業を保留する

**ユーザーへの報告**

以下の情報を含む報告を行う：
```
【衝突検出】または【不明確な点の検出】

■ 検出内容：
- 具体的な衝突・矛盾・不明点の説明

■ 影響範囲：
- 影響を受ける既存ドキュメント
- 影響を受ける機能・コンポーネント

■ 提案または質問：
- 解決案の提示（複数案がある場合はすべて列挙）
- ユーザーへの確認事項
- 必要な追加情報

■ 次のアクション：
- ユーザーの決定を待つ具体的な項目
```

**明確な回答を待つ**
- ユーザーから明確な指示・決定を受けるまで待機
- 曖昧な回答の場合は再度確認を求める

#### **3. 実行フェーズ**

ユーザーから明確な回答・承認を得た後：

**変更の実施**
- 承認された内容に基づいてドキュメントを更新
- 影響範囲のすべてのドキュメントを同時に更新

**整合性の確保**
- 関連するすべてのドキュメントの一貫性を確認
- 変更履歴に衝突解決の経緯を記録

### **禁止事項**

以下の行為は**絶対に禁止**：
- ❌ 衝突を検出したまま作業を続行する
- ❌ 独断で衝突を解決する
- ❌ 不明確な点を推測で補完する
- ❌ ユーザーへの確認なしに既存仕様を変更する
- ❌ 影響範囲の分析を省略する

## 変更影響分析ルール

### **影響範囲の追跡**

設計変更を行う際は、以下の影響分析を**必ず**実施すること：

**1. 上流への影響**
- 要件定義への影響確認
- ビジネス目標との整合性確認

**2. 同レベルへの影響**
- 他のコンポーネント設計への影響
- インターフェース仕様への影響
- データモデルへの影響

**3. 下流への影響**
- 実装への影響予測
- テスト計画への影響
- デプロイメントへの影響

### **トレーサビリティマトリクス**

要件と設計要素の双方向追跡を維持：

| 要件ID | 機能名 | 画面 | API | データモデル |
|--------|--------|------|-----|-------------|
| REQ-001 | ユーザー登録 | 01_User_Registration.md | 01_User_API.md | users テーブル |
| REQ-002 | タスク作成 | 02_Task_Create.md | 02_Task_API.md | tasks テーブル |

### **変更記録の必須項目**

- **変更日時**: YYYY-MM-DD HH:MM
- **変更者**: 担当者名
- **変更理由**: ビジネス要因または技術要因
- **影響範囲**: 影響を受けるドキュメント・コンポーネントのリスト
- **決定事項**: 何をどのように変更したか
- **承認者**: レビュー・承認した責任者

## まとめ

### **重要なポイント**

1. **順序を守る**: DB → 画面 → API → 詳細設計
2. **整合性を継続的に確認**: 各フェーズで前工程との整合性を確認
3. **機能単位でイテレーション**: すべてを一度に設計しない
4. **ガイドライン・テンプレートを活用**: 一貫性を保つ
5. **モックアップを真実とする**: 画面設計はモックアップに準拠
